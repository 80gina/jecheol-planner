## 1. 무엇을 분석했나

평생학습센터 요리교실을 운영하면서 되풀이되는 문제가 있습니다.
**한 달 전에 짠 식단표의 재료비가 수업 당일에 맞지 않습니다.**

"제철에 사면 싸다"는 말은 누구나 합니다. 그런데
**"그래서 12월에는 6월보다 몇 퍼센트 더 내야 하는가"** 는 검색으로 나오지 않습니다.

| **기온** | 기상청 지상관측(ASOS) 일자료 · 창원(지점 155) · 731일 |
| **데이터 포인트** | 품목당 약 500개 (과제 요구 100개 이상) |

## 3. 분석 대상 9품목 — 짝을 지어 골랐다

재료를 하나씩 고르지 않고 **비교 쌍**으로 골랐습니다. 혼자 있는 숫자는 해석이 안 되기 때문입니다.

| 짝 | 품목 | 확인하려는 것 |
|---|---|---|
| **정반대 짝** | 시금치 ↔ 오이 | 겨울 제철 vs 여름 제철 — 곡선이 거울처럼 뒤집히는가 |
| **같이 가는 짝** | 배추 ↔ 무 | 둘 다 김장 수요 — 같은 달에 같이 오르는가 |
| **닮은 짝** | 감자 ↔ 고구마 | 둘 다 저장 작물 — 저장이 계절성을 얼마나 눌러주는가 |
| **대조군** | 양파 | 저장·유통 기간이 길어 **계절 변동이 가장 작을** 품목 |
| **공통 재료** | 대파 | 거의 모든 메뉴에 들어감 |
| **소액 재료** | 애호박 | 값은 작지만 12인 수업에서 누적됨 |

> **대조군을 넣은 것이 이 분석의 설계 핵심입니다.**
> "배추는 겨울에 비싸다"만 보여주면 "원래 다 그런 것 아니냐"는 반문을 막을 수 없습니다.
> 계절성이 **없는** 품목을 나란히 놓아야 "다른 건 안 그런데 배추만 그렇다"가 성립합니다.

### 콩나물을 뺀 이유

처음 대조군은 콩나물이었습니다(실내 재배라 계절성이 없을 것으로 봄).
그런데 `probe` 로 확인해 보니 **KAMIS 채소류 품목 목록 31종에 콩나물이 없었습니다.**
추측으로 코드를 적지 않고 **실제 응답을 확인한 뒤 양파로 교체**했습니다.

## 4. 빠른 시작

```bash
git clone https://github.com/80gina/jecheol-planner
cd jecheol-planner
pip install -r requirements.txt
```

### 인증키 준비

```bash
copy .env.example .env      # Windows
```

`.env` 에 두 가지를 채웁니다.

| 키 | 어디서 | 비고 |
|---|---|---|
| `KAMIS_CERT_KEY` / `KAMIS_CERT_ID` | [kamis.or.kr](https://www.kamis.or.kr) → 고객센터 → Open-API | 인증키 + **신청 이메일** 두 개가 필요 |
| `KMA_SERVICE_KEY` | [data.go.kr](https://www.data.go.kr) → `기상청_지상(종관, ASOS) 일자료` → 활용신청 | **일반 인증키(Decoding)** 를 넣을 것 |

> ⚠️ **Encoding 키를 넣으면 인증에 실패합니다.** `%2F`, `%2B`, `%3D` 가 들어간 쪽이 Encoding 키입니다.
> 프로그램이 요청을 보낼 때 다시 인코딩하므로, 이미 인코딩된 것을 넣으면 **두 번 인코딩**됩니다.
>
> ⚠️ 공공데이터포털은 인증키를 **계정당 하나** 발급하지만 **서비스별로 따로 활용신청**을 받습니다.
> 키가 있어도 그 서비스에 신청이 안 돼 있으면 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 납니다.

### 실행 순서

```bash
python main.py basket              # 1. 분석 대상 확인 (인증키 없이 동작)
python main.py probe --date 2026-09-04   # 2. KAMIS 응답 구조 확인
python main.py codes               # 3. 품목 코드를 KAMIS 에서 받아 저장
python main.py collect --years 2   # 4. 2년치 가격 수집 → data/prices_raw.csv
python main.py weather --years 2   # 5. 기온 수집 → data/weather_raw.csv
python main.py analyze             # 6. 정제·분석·그래프 → images/
```

**중간에 멈춰도 됩니다.** 품목 하나가 끝날 때마다 저장되므로
`python main.py collect --years 2 --resume` 으로 이어받습니다.

## 7. 데이터 정제 기준

| 무엇 | 기준 | 왜 이렇게 정했나 |
|---|---|---|
| **달력** | 월~금 영업일만 센다 | 주말은 애초에 시세 조사를 하지 않는다. 주말을 만들어 메우면 **없는 거래를 지어내는 것**이 된다 |
| **결측** | 연속 3일 이하만 선형보간 | 연휴 정도는 앞뒤를 이어도 되지만, 길게 빈 구간까지 메우면 데이터를 창작하는 셈 |
| **이상치** | 31일 **이동중앙값** 대비 ±50% 밖 | 평균이 아니라 **중앙값**을 쓴 것이 핵심. 평균은 튄 값 자체에 끌려가서 이상치를 못 잡는다 |
| **지역** | `countyname` 이 **"평균"** 인 행만 | 기간 조회는 지역·시장별로 행을 쪼개 준다(하루 37행). 그대로 쓰면 같은 날 값이 수십 개가 된다 |
| **품종** | 같은 날 여러 품종이면 **중앙값**으로 합침 | 배추·무는 품종이 **계절마다 교대**한다(여름 고랭지 → 월동). 하나만 남기면 나머지 계절이 통째로 빈다 |
| **등급** | 상품(04) 고정 | 상품·중품이 섞이면 하루에 값이 두 개가 된다 |

## 8. 적용한 시계열 분석 기법

과제 요구는 2가지 이상. **5가지**를 적용했습니다.

| # | 기법 | 왜 필요했나 |
|:-:|---|---|
| 1 | **이동평균** 7일 · 30일 | 일별 원본은 잔떨림이 심해 방향이 안 보인다. 두 선이 **갈라지는 지점**이 방향 전환 신호 |
| 2 | **변화율** 1일 · 30일 | 급등·급락이 **언제** 일어났는지 찾기 위해 |
| 3 | **월별 계절 지수** | 배추(4천 원대)와 애호박(1천5백 원대)을 한 그림에 못 올린다. **연평균=100** 으로 단위를 통일 |
| 4 | **변동계수** (표준편차÷평균) | 표준편차만 보면 "비싼 품목이 많이 흔들린다"는 당연한 결론만 나온다 |
| 5 | **시계열 분해** (보너스) | 물가 상승분과 계절 변동을 갈라 봐야 "실제로 얼마나 오른 것인가"가 나온다 |

### statsmodels 를 쓰지 않은 이유

`seasonal_decompose()` 를 부르면 한 줄로 끝납니다. 그러나 이 과제의 목표가
**"트렌드·계절성·노이즈 개념을 설명할 수 있다"** 입니다.
라이브러리를 부르면 결과는 나오지만 **어떻게 분해했느냐에 답할 수 없습니다.**

고전적 가법 분해는 이동평균 세 번이면 되므로 직접 구현했습니다 (`analyze.decompose`).

```
1) 추세   : 1년치(영업일 261일) 중심 이동평균
            → 한 해를 통째로 평균 내면 계절 성분이 상쇄되고 긴 흐름만 남는다
2) 계절성 : (원본 − 추세) 를 '몇 월 며칠인가'로 묶어 평균
            → 12월 31일과 1월 1일이 이어지도록 앞뒤로 한 바퀴씩 붙여 평활
3) 잔차   : 원본 − 추세 − 계절성
```

> **양 끝을 비워 둔 이유**: 1년 창이 다 차지 않는 구간은 추세를 계산하지 않습니다.
> 절반만 채워 계산하면 **없는 추세가 만들어져 보입니다.**
> 모르는 구간은 비워 두는 편이 정직합니다.

### 이중축을 쓰지 않은 이유

기온(℃)과 가격(원)은 단위가 전혀 다릅니다. 한 그림에 세로축을 둘 두면
**두 선이 만나는 지점이 아무 뜻도 없는데 뜻이 있어 보입니다.**
가로축을 기온, 세로축을 가격지수로 놓으면 축은 하나씩만 쓰면서 관계를 볼 수 있습니다.

> ⚠️ **상관은 인과가 아닙니다.** 기온이 낮은 달에 비싸다 해도,
> 추워서인지 김장 수요 때문인지 이 그림만으로는 못 가릅니다.
> 리포트에서는 **관찰**로만 쓰고, 원인은 **가설**로 분리해 적습니다.

처음에는 `pandas==2.2.3` 처럼 못 박았습니다. 그런데 파이썬 버전이 새로우면
**그 버전에 맞는 설치 파일(wheel)이 없어** pip이 소스 빌드로 넘어가고,
Visual Studio 빌드 도구가 없어 실패합니다.

그래서 `pandas>=2.2` 처럼 **하한만** 두었습니다.
학습·과제 환경에서는 버전 고정이 재현성을 높이기보다 **환경을 가립니다.**

## 12. 겪은 문제와 해결

이 프로젝트에서 외부 API 때문에 겪은 문제들입니다. 같은 API를 쓰실 분께 도움이 될 것입니다.

| 증상 | 원인 | 해결 |
|---|---|---|
| `metadata-generation-failed` (pandas 설치 실패) | 버전을 고정해 wheel 이 없어 소스 빌드로 감 | `==` → `>=` |
| `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` | 키는 계정당 하나지만 **서비스별로 따로 신청**해야 함 | 해당 서비스에 활용신청 |
| 인증 실패 (기상청) | **Encoding 키**를 넣어 두 번 인코딩됨 | Decoding 키로 교체 |
| `resultCode 99` — "전날 자료까지" | ASOS 일자료는 하루가 끝나야 확정 | 끝 날짜를 **어제**로 |
| 수집 결과의 **날짜가 전부 동일** | 1년 구간 요청 시 **빈 응답**이 와서 마지막 하루치만 모임 | 구간을 나눠 요청 + **빈 응답이면 절반으로 쪼개 재시도** |
| `ReadTimeout` | 구간이 커서 서버가 응답을 못 만듦 | 재시도 1회로 줄이고 **바로 쪼개기** |
| 결측이 품목당 220일 | 매일 달력으로 만들어 **주말이 결측으로 잡힘** | 영업일 달력으로 변경 → 5~17일 |

### 배운 것 두 가지

**① "수집 성공"과 "제대로 수집됨"은 다릅니다.**
행 수만 보고 넘어갔다가, CSV를 열어 **날짜 분포**를 확인하고 나서야 문제를 발견했습니다.

**② 같은 API라도 액션이 다르면 응답도 다릅니다.**
하루치 조회의 응답 구조는 확인했으면서 기간 조회는 짐작으로 파서를 짰다가 틀렸습니다.
그래서 `probe-period` 명령을 따로 만들었습니다 — **확인하고 나서 짠다.**
