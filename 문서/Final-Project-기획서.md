# 제철밥상 요리교실 AI 준비실 — Final Project 기획서

> 코디세이 AI 네이티브 Final Project (자율 주제) · 작성 김진아 · 2026-09-10
> 필수 기술 요소: **AI Agent** + **멀티모달 AI** (2개 이상 요건 충족)

---

## 1. 문제 정의

### 1-1. 현장에서 실제로 겪은 문제

창원 웅남평생학습센터에서 시니어 대상 요리교실을 운영하면서 겪는 문제는 세 가지다.

**① 재료비 예산이 실제 시세와 어긋난다.**
수업 두 달 전에 예산을 확정하는데, 그때 잡은 재료비가 수업 당일 시세와 다르다. 실제로 확인된 사례가 있다.

| 품목 | 기획 때 쓴 값 | KAMIS 실측 (2026-09-09) | 차이 |
|---|---|---|---|
| 배추 (여름 고랭지 1포기) | 4,320원 | **6,000원** | +39% |
| 애호박 (1개) | 1,650원 | **2,815원** | +71% |

12인 수업 기준으로 배추 한 품목에서만 약 2만 원이 어긋난다. 4회차면 예산 전체가 흔들린다.

**② 시장에서 즉석 판단을 할 수 없다.**
장을 보다가 값이 좋은 재료를 봐도, 그게 평소보다 싼 건지 비싼 건지 그 자리에서 알 수 없다. 알아도 그 재료로 수업 메뉴를 바꾸려면 레시피·장보기·예산·안내문을 전부 다시 짜야 해서 사실상 못 바꾼다.

**③ 수업계획안 작성에 시간이 너무 든다.**
회차별 메뉴 선정 → 선정 근거 작성 → 학습목표 → 안전안내 → 진행 시간표 → 장보기 목록 → 참가자 안내문. 4회차 한 기수를 준비하는 데 반나절이 걸린다. 그런데 이 작업의 대부분은 시세·뉴스·레시피라는 이미 있는 데이터를 조합하는 일이다.

### 1-2. 왜 AI가 필요한가

세 문제 모두 "데이터는 있는데 사람이 조합하는 데 시간이 든다"는 형태다. 조건(지역·인원·예산·알레르기·날짜)이 매번 달라서 규칙으로 고정할 수 없고, 판단 근거를 말로 설명해야 해서 단순 계산으로도 안 된다. 도구를 호출해 사실을 모으고, 그 사실 위에서 판단하고, 근거를 문장으로 설명하는 일 — AI Agent가 하는 일 그대로다.

②의 "시장에서 사진 한 장"은 텍스트 입력으로는 성립하지 않는다. 좌판 위 재료와 손글씨 가격표를 사람이 타이핑하는 순간 그 자리에서 쓸 수 없는 도구가 된다. 멀티모달이 필요한 이유가 편의가 아니라 **성립 조건**이다.

## 3. 서비스 개요

**한 줄 정의** — 시장 사진 한 장과 몇 가지 조건만 주면, 실측 시세를 근거로 요리교실 회차 계획을 통째로 짜 주는 AI 준비실.

### 3-1. 두 축이 하나로 이어진다

```
[멀티모달]  시장에서 사진 촬영
              ↓  재료 인식 + 가격표 판독
            "고등어, 좌판 표시가 6,000원"
              ↓  KAMIS 실측 시세 대조
            "전국 평균보다 12% 비쌈 — 오늘은 보류"
              ↓
[AI Agent]  "그럼 이 조건으로 3회차 다시 짜 줘"
              ↓  도구 호출 (시세·뉴스·레시피·명단·예산)
            회차 구성 + 선정 근거 + 장보기 + 예산 + 안내문 초안
```

사진이 에이전트의 입력이 되고, 에이전트가 그 재료로 계획을 다시 짠다. 두 기능이 각자 노는 게 아니라 하나의 동선이다.

## 4. AI 활용 방식

### 4-1. AI Agent — 커리큘럼 에이전트

**하는 일**: 자연어 조건을 받아 필요한 도구를 스스로 골라 호출하고, 모은 사실 위에서 회차 계획을 만든다.

입력 예시:
> "창원, 어르신 10명, 1인 7천 원, 4회차, 갑각류 알레르기 있는 분 두 명. 10월 매주 목요일."

**도구 목록 (Function Calling)**

| 도구 | 하는 일 | 데이터 출처 |
|---|---|---|
| `get_price(품목, 지역)` | 실측 소매가·전주·전년 대비 조회 | `05_시세` (KAMIS 실측) |
| `get_news(품목)` | 최근 2년 이내 검증된 기사 조회 | `09_뉴스` |
| `search_recipe(조건)` | 조리시간·난이도·알레르기 조건으로 레시피 검색 | `07_레시피` |
| `get_roster(교실ID)` | 확정 참가자 수·알레르기 집계 (**익명 ID만**) | `01_참가신청` |
| `estimate_budget(메뉴, 인원)` | 재료비 합계 계산 | 계산 |
| `save_plan(계획)` | 확정된 계획을 시트에 기록 | `02~04` |

**환각을 막는 설계 — 이 서비스의 핵심 제약**

가격을 지어내면 예산이 틀리고, 예산이 틀리면 실제 손해가 난다. 그래서 세 겹으로 막는다.

1. **가격·기사는 반드시 도구 결과만 인용한다.** 모델이 아는 값을 쓰는 것을 시스템 프롬프트에서 금지한다.
2. **모든 숫자에 출처와 기준일을 붙인다.** "배추 6,000원 (KAMIS 실측, 2026-09-09 기준)". 출처를 못 붙이는 숫자는 답변에 넣지 않는다.
3. **데이터가 없으면 없다고 말한다.** 현재 KAMIS 장바구니에 전어·대하·무화과는 없다. 이 품목을 물으면 추정값을 내지 않고 "시세 데이터가 없어 예산 근거로 쓸 수 없습니다"라고 답한다.

이 원칙은 이미 앞선 과제에서 필요성이 확인됐다. 뉴스 수집 단계에서 존재하지 않는 기사 URL이 생성되는 문제를 겪었고, 그 뒤로 "모든 URL은 열어서 제목·날짜를 대조한 뒤에만 저장"이라는 규칙을 넣었다. 같은 원칙을 가격에도 적용한다.

**2단계 구조**

```
Planning Agent  조건 해석 → 필요한 도구 판단 → 호출 → 회차 초안 생성
      ↓
Verify Agent    초안 검증: ① 예산 초과 ② 알레르기 위반
                          ③ 출처 없는 숫자 ④ 난이도·조리시간이 대상에 맞나
      ↓
검증 통과분만 사용자에게 제시 (실패 항목은 이유와 함께 표시)
```

Verify 단계를 분리한 이유: 생성한 주체가 스스로 검토하면 자기 결과를 옹호한다. 알레르기 위반은 실제 안전 문제라 별도 검증이 필요하다.

### 4-2. 멀티모달 AI — 시장 재료 인식

**하는 일**: 사진 한 장에서 재료와 가격표를 함께 읽고, 실측 시세와 대조해 살지 말지를 판단한다.

```
① 촬영          스마트폰으로 좌판 촬영
② 인식          Vision 모델 → 재료 후보 3개 + 신뢰도
                가격표가 찍혀 있으면 표시 금액도 함께 판독
③ 사용자 확정   후보 중 선택 (또는 직접 입력)   ← 생략 불가
④ 코드 매핑     확정된 이름 → KAMIS 품목코드
⑤ 시세 대조     실측 시세 조회 → 좌판 가격과 비교
⑥ 판정          🟢 사기 좋음 / 🟡 평년 수준 / 🔴 비쌈
⑦ 연결          "이 재료로 회차 바꾸기" → AI Agent로 전달
```

**③ 사용자 확정 단계를 반드시 넣는 이유.** 이미지 인식은 틀린다. 애호박과 주키니, 대파와 쪽파는 사진으로 구분이 어렵다. 틀린 재료로 예산을 짜면 처음의 문제로 되돌아간다. 그래서 인식 결과를 확정이 아니라 **후보 제시**로 다루고, 사람이 고른 것만 다음 단계로 넘긴다. 신뢰도가 낮으면 그 사실을 화면에 표시한다.

**가격표 판독이 이 기능의 진짜 값어치다.** KAMIS는 전국 평균이고, 시장 좌판 가격은 그와 다르다. 두 값을 나란히 보여줘야 "이 가게가 싼 건가"에 답할 수 있다.

> 예: 좌판 표시 6,000원 · KAMIS 전국 평균 5,350원 → **12% 비쌈. 옆 가게를 보고 오세요.**

## 5. 기술적 접근

### 5-1. 기술 스택과 선정 이유

| 영역 | 선택 | 선정 이유 |
|---|---|---|
| Backend | **FastAPI (Python)** | 기존 KAMIS 수집 코드(`kamis.py`, `price.py`)가 Python이라 그대로 가져다 쓴다. 새로 짜지 않는다. |
| LLM | **Claude API** | Function Calling과 Vision을 **한 API로** 처리한다. Agent용·Vision용 모델을 따로 쓰면 키 관리·오류 처리·비용 추적이 두 벌이 된다. |
| 데이터 | **Google Sheets** (유지) + SQLite (캐시) | 시트를 고른 이유는 성능이 아니라 **비개발자가 직접 열어보고 고칠 수 있어서**다. 센터 직원이 참가자 명단을 확인해야 하는데 DB는 열어볼 수 없다. 조회 성능은 SQLite 캐시로 보완한다. |
| Frontend | 기존 HTML 앱 개조 | 이미 만들어 쓰고 있는 화면(9개 탭)이 있다. 이걸 백엔드 호출로 바꾸는 게 처음부터 만드는 것보다 빠르고, 사용자가 이미 익숙하다. |
| 자동화 | 기존 수집 파이프라인 | `collect` → `price` → 시트 반영이 이미 동작한다. |
| 배포 | Render (API) + Vercel (프론트) | 무료 티어로 충분한 규모. |

**"이미 있는 것을 쓴다"가 스택 선정의 축이다.** 5개월간 만든 것 — KAMIS 수집기, 레시피 9종, 검증된 뉴스, 구글시트 DB, 9개 탭 화면 — 이 전부 그대로 자산이다. Final Project에서 새로 만드는 것은 **AI 계층 하나**다.

### 5-2. 시스템 구성

```
[웹앱]  시세·메뉴 / 수업계획안 / 장보기 / 신청 / 사진 등록
   │
   ├── POST /agent/plan      조건 → 회차 계획
   ├── POST /vision/identify 사진 → 재료 + 가격표
   └── GET  /price /news     조회
   │
[FastAPI]
   ├── Agent Orchestrator ── Planning → Verify
   │        └── Tools: price / news / recipe / roster / budget / save
   ├── Vision Handler ────── 인식 → 후보 → 코드 매핑
   └── Data Layer ────────── SQLite 캐시 ⇄ Google Sheets
   │
[외부]  Claude API · KAMIS OpenAPI · Google Sheets API
```

### 6-2. 비기능 요구사항 (NFR)

| ID | 항목 | 요구사항 |
|---|---|---|
| NFR-01 | 응답 속도 | Vision 인식 5초 이내 / Agent 계획 생성 30초 이내 (진행 표시 필수) |

## 10. 검증 계획

**환각 방지 검증 (NFR-02)** — 계획 생성 30건을 돌려, 답변에 등장한 모든 숫자가 도구 호출 로그의 값과 일치하는지 자동 대조한다. 불일치 0건이 목표이며, 이 수치를 발표에 넣는다.

**Vision 정확도** — 시장에서 촬영한 재료 사진 50장으로 1순위 후보 적중률과 3순위 내 적중률을 측정한다. 목표는 3순위 내 90%. 1순위만으로 자동 확정하지 않는 설계 근거가 이 수치다.

**실사용자 테스트** — 수강생 10명 + 강사 2명. 측정 항목: ① 수업계획안 작성 시간 (기존 반나절 대비) ② 예산 오차율 ③ 시장에서 실제로 써봤는지.

## 11. 앞선 과제와의 관계

이 프로젝트는 Project B에서 만든 `bapsang-trend`(뉴스 트렌드 분석)와 `jecheol-planner`(시세 수집)를 기반으로 한다. 선을 분명히 해 둔다.

| | Project B | Final Project |
|---|---|---|
| 성격 | 데이터 **분석 리포트** | AI **서비스** |
| 결과물 | CLI + 분석 문서 | 배포된 서비스 + 실사용자 |
| AI | 없음 (통계 분석) | Agent + 멀티모달이 핵심 |
| 사용자 | 없음 (본인 분석용) | 강사·수강생 12명 이상 |

Final Project는 앞 과제가 만든 **데이터를 소비하는 쪽**이다. 같은 주제를 다시 내는 것이 아니라, 5개월간 쌓은 자산 위에 AI 계층을 얹어 실제 사용자에게 전달하는 단계다.
